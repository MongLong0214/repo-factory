# Phase 5 상세 — 웨이브 실행 프로토콜

## 1. 웨이브 설계

### 키스톤 먼저
의존성 그래프에서 **가장 많은 티켓을 막고 있는 노드**를 찾는다. 보통 파서·스키마·코어 타입 같은 것. 이걸 1번 웨이브에 넣지 않으면 나머지 병렬화가 무의미하다.

### 파일 소유권으로 분할
```
웨이브 = { 에이전트 → 소유 파일 집합 }
```
두 에이전트의 소유 집합이 겹치면 웨이브 설계가 틀린 것이다. 겹치면 (a) 순차로 돌리거나 (b) 소유권을 재분할하거나 (c) `isolation: "worktree"`로 격리한다.

**공유 파일 규칙**: `package.json`, CLI 엔트리, 공용 타입 파일은 **한 에이전트만 소유**. 나머지 프롬프트에 명시:
> "`package.json`은 다른 에이전트가 생성 중이다. 만들지도 수정하지도 마라. 의존성 추가가 필요하면 보고하라."

**CLI 엔트리는 리더가 소유하고, 에이전트는 등록 함수만 내보낸다.** 명령이 여럿인 CLI에서 모든 에이전트가 엔트리 파일을 편집하면 충돌이 확정된다. 계약을 프롬프트에 박아라:
```ts
// src/commands/<name>.ts — 에이전트 소유
export const register = (program: Command): void => { program.command('<name>')... };
// src/cli.ts — 리더가 소유. import 한 줄 + 호출 한 줄만 추가한다.
```

### ⚠️ 편집자만 보지 말고 **실행자**도 봐라

파일 소유권은 보통 "누가 이 파일을 **쓰는가**"로 나눈다. 그것만으로는 부족하다. **누가 이 파일을 지금 실행하고 있는가**도 소유권이다.

실측 사례: 벤치마크 에이전트가 60런짜리 측정을 **실행하는 중에**, 다른 에이전트에게 그 실행이 읽는 파일들의 **편집** 소유권을 줬다. 43/60 시점에 변경이 들어갔다.

결과적으로 **측정 자체는 오염되지 않았다** — 러너가 정적 import만 쓰는 단일 프로세스라 디스크 변경이 도달하지 못했다(`research-protocol.md` §3-d: mtime으로 실행 중 코드를 추론하지 마라). 하지만 그 파일은 여전히 폐기해야 했다: **수치를 만든 코드가 저장소에 더 이상 존재하지 않아 재현이 불가능**해졌기 때문이다.

⚠️ 그리고 런마다 프로세스를 새로 띄우는 하네스였다면 **실제로 데이터가 분할됐을 것이다.** 어느 쪽인지는 하네스 구조에 달렸고, 그걸 확인하기 전에는 알 수 없다.

같은 함정의 다른 모양:
- 장기 실행 중인 서버·워커의 소스를 다른 에이전트가 편집
- 마이그레이션이 읽고 있는 스키마 파일을 동시에 수정
- 빌드가 진행 중인 설정 파일 교체

**웨이브를 설계할 때 물어라: 지금 돌고 있는 프로세스가 어떤 파일을 읽는가?** 그 파일들은 실행이 끝날 때까지 **동결**이다. 장기 실행 작업이 있으면 그 소유권을 명시적으로 선언하라 —
> "`bench/runner.ts`·`src/core/inject.ts`는 T-702의 매트릭스가 **실행 중**이다. 종료 전까지 동결. 편집이 필요하면 보고하고 대기하라."

이미 벌어졌다면: 되돌리지 마라(되돌리는 것도 변경이다). 실행 중인 작업을 **파일럿으로 강등**하고, 코드를 동결한 뒤 다시 돌려라. 시간이 아까워 보여도, 생성 코드가 도중에 바뀐 수치를 발표하는 것보다 싸다.

### ⚠️ 검증 명령의 스코프도 나눠라 — 파일 소유권만으로는 부족하다

파일을 안 겹치게 나눠도 **`npm test` / `tsc` 는 저장소 전체를 본다.** 5개 에이전트가 동시에 돌면 각자가 남의 반쯤 쓴 테스트·타입 에러를 보고, "내가 뭘 깼나" 하고 **남의 파일을 고치기 시작한다.** 이게 파일 소유권 규칙을 우회하는 경로다.

프롬프트에 반드시:
- 작업 중 검증은 **자기 테스트 파일만**: `npx vitest run test/<mine>.test.ts`
- 전체 타입체크에서 나온 에러는 **자기 소유 파일에서 나온 것만** 고친다
- 남의 파일에서 에러가 보이면 **고치지 말고 보고만** 한다 ("타 에이전트 파일 X에서 에러 관측, 내 소관 아님")
- 전체 테스트는 마지막에 참고용 1회. 남의 실패가 자기 완료를 막지 않는다. **통합은 리더가 한다**

이미 스폰한 뒤에 깨달았다면 늦지 않았다 — 실행 중인 에이전트에게 정정 메시지를 보내라. 조용히 두면 서로의 코드를 덮어쓴 결과를 나중에 되돌려야 한다.

### 선행 착수로 대기 줄이기
후속이 선행의 *산출물*이 아니라 *인터페이스*만 필요하면 인터페이스를 프롬프트에 박아 병렬 착수시킨다. 정본(공개 README·스펙 초안)이 있으면 그것을 근거로 삼게 하고:
> "불일치를 발견하면 <정본>을 따르고 보고하라."

### 전형적 웨이브 형태
| 웨이브 | 성격 |
|---|---|
| 1 | 키스톤 + 완전 독립 트랙(벤치·스캐폴딩) |
| 2 | 키스톤 직속 의존 (스키마·픽스처) |
| 3 | **최대 팬아웃** — disjoint 모듈 4~5개 동시 |
| 4 | 통합 계층 (훅·서버·어댑터) |
| 5 | 외부 표면 (CI Action·릴리스 준비) |
| 6 | 릴리스 |

동시 3~5개 유지. 리뷰가 병목이면 병렬성을 줄인다 — 리뷰를 줄이지 않는다.

## 2. 서브에이전트 프롬프트 골격

```
작업 디렉토리: <절대경로>

너의 임무: 티켓 T-XXX (issue #N) 구현 — <한 줄>
[키스톤이면] 이건 키스톤이다 — N개 티켓이 네 인터페이스 위에 올라간다.

## 병렬 작업 중인 다른 에이전트 (충돌 방지)
- A: <파일> 작업 중 → 건드리지 마라
- B: <파일> 생성 중 → 만들지도 수정하지도 마라. 필요하면 보고하라
[파일이 아직 없을 수 있으면 대기 절차와 타임아웃, 실패 시 행동까지 지정]

## 먼저 읽어라
1. docs/tickets/F<n>-*.md — T-XXX 항목이 네 스펙
2. docs/prd/... , docs/adr/... (관련된 것만)
3. <정본 문서> — 불일치 시 이걸 따르고 보고

## 산출물
파일별로: 경로 / 역할 / 시그니처 / 필수 동작

## 테스트
필수 케이스 목록 (경계·실패 포함)

## 제약
- 코드 컨벤션 (기존 선례 파일 지목)
- 과잉 추상화 금지 — 지금 필요한 것만
- 추측 금지: 모르면 임시 환경에서 실제로 실행해 확인하고, 확인 결과를 보고서에 남겨라
- 네트워크/외부 호출 정책

## 완료 후
1. 커밋하지 마라 (CTO 리뷰 후 내가 커밋한다)
2. 보고 필수: 파일 목록 / **테스트 실제 출력** / 직접 확인한 경계 동작 / 정본과의 불일치 / 요청할 의존성
   **실행하지 않은 것을 통과했다고 쓰지 마라.**
```

### 모델 선택
- `opus` — 파서·동시성·보안·인덱스·성능·벤치 설계·마이그레이션. 판단 불확실성이 큰 것
- `sonnet` — 문서화·픽스처·번역·배선·템플릿. 규격이 명확한 것
- 애매하면 opus. 재작업 1회 비용이 항상 더 크다

### 0단계 — 스폰 전에 실행 모드부터 확인하라 ⚠️ 최우선

**웨이브를 띄우기 전에 반드시:**
```bash
grep teammateMode ~/.claude/settings.json ; echo "TMUX=${TMUX:-<none>}"
```

| `teammateMode` | tmux 안? | 결과 |
|---|---|---|
| `in-process` | 무관 | 정상 동작 |
| `tmux` | 예 | 정상 동작 |
| `tmux` | **아니오** | ☠️ **전 에이전트가 영원히 정체한다** |

`tmux` 모드인데 tmux 밖에서 실행 중이면 에이전트마다 존재하지 않는 pane ID를 배정받고 입출력을 기다리며 멈춘다. 스폰은 성공으로 보고되고, 프로세스도 살아 있고, 산출만 영원히 0이다. 실측 사례: 이 조합으로 서브에이전트 10개가 연속으로 죽었고 원인을 찾는 데 두 세션이 걸렸다.

발견 시 조치: `settings.json`의 `teammateMode`를 `"in-process"`로 바꾼다. **단 설정은 프로세스 기동 시 캐시되므로 지금 세션에는 적용되지 않는다** — 새 세션에서만 유효하다. 지금 진행해야 하면 §직접 수행 폴백으로 간다.

### 생존 확인 — 판정 방법이 모드마다 다르다 ⚠️

**이 절은 두 번 틀렸다.** 처음엔 인박스·트랜스크립트를 근거로 삼았다가 오진이었고, 다음엔 "프로세스 테이블이 유일한 진실"로 고쳤는데 그것도 **tmux 모드에서만** 맞았다. 정확한 규칙은 아래다.

#### `in-process` 모드 (기본 권장)
에이전트가 메인 프로세스 **안에서** 돈다. **`ps`에 `--agent-name`으로 절대 잡히지 않는다.** `ps`가 비었다고 죽은 게 아니다 — 이 모드에서 `ps`는 판정 근거가 될 수 없다.

유효한 신호는 **산출 파일의 mtime**뿐이다:
```bash
# 최근 2분 내 쓰기가 있었나 = 살아서 일하는 중
find <소유디렉토리> -type f -mmin -2
# 최근 산출 5개를 시각과 함께 (macOS: stat -f, Linux: stat -c '%Y %n')
find <소유디렉토리> -type f -exec stat -f '%m %N' {} \; | sort -rn | head -5 | \
  while read -r m n; do echo "$(date -r "$m" '+%H:%M:%S') $n"; done
```

> ⚠️ **`-newermt '-90 seconds'` 를 쓰지 마라.** 상대 시각 문법은 GNU findutils 전용이다. macOS 기본 `find`와 `bfs`에서는 파싱 실패하는데, 셸에 따라 **조용히 0건을 반환**해서 "죽었다"는 오진을 만든다. 실측으로 이 함정에 걸렸다. `-mmin` 은 BSD·GNU·bfs 전부에서 동작한다.
그리고 **완료 통지가 최종 진실이다.** 통지가 오기 전에 산출물을 읽고 판정하지 마라 — 반쯤 쓰인 파일을 완성본으로 오독한다.

#### `tmux` / 별도 프로세스 모드
이때만 프로세스 테이블이 유효하다:
```bash
ps -eo pid,etime,args | grep -- "--agent-name" | grep -v grep | \
  sed -n 's/.*--agent-name \([^ ]*\).*/\1/p'
```
⚠️ 다른 세션의 좀비가 섞인다. `--parent-session-id`로 **내 세션 것만** 걸러라. 실측으로 22시간짜리 좀비 8개가 남아 있는 환경을 봤다.

#### 모드 무관하게 쓰지 마라 — 실측으로 확인된 거짓 신호
| 신호 | 왜 틀리나 |
|---|---|
| 인박스 `read: false` | 정상 기동·작업 중인 에이전트도 `false`로 남는다 |
| `subagents/` 트랜스크립트 부재 | 진행 중에는 아직 안 만들어질 수 있다 |
| `tmux list-panes` | config의 `tmuxPaneId`는 실제 페인과 무관할 수 있다 |
| 산출 파일 없음(단발 관찰) | opus/고effort는 20분 넘게 읽기·설계만 하기도 한다. **mtime 변화**를 보라, 존재 여부가 아니라 |

**두 가지 실패를 구분하라:**
- **미기동** — 스폰 후 수 분간 산출 mtime이 전혀 안 움직인다 → 재스폰 또는 직접 수행
- **정체(hang)** — 살아 있는데 오래 무산출. 판정 기준: *예상 소요의 3배 초과 + mtime 정지*. 프롬프트 과대·범위 과대를 의심하고 재설계한다

#### ⚠️ 완료 보고를 기다리지 마라 — 산출물을 검증하라

실측: 한 세션에서 서브에이전트 **10개 이상이 산출물을 전부 전달했는데 완료 통지는 한 건도 도착하지 않았다.** 파일은 제때 들어왔고, 테스트도 통과했고, 통지만 오지 않았다.

통지를 기다리면 공장이 멈춘다. 그리고 어차피 **CTO 게이트는 보고서를 믿지 않는다**(§3-2 "내가 직접 실행"). 그러니 판정 근거를 처음부터 산출물에 두어라:

- 진행 판정: 소유 디렉토리의 **mtime**
- 완료 판정: **네가 직접 돌린** 타입체크·테스트·스위트가 통과하는가
- 보고서는 오면 **보너스**다 — 에이전트가 스스로 발견한 경계나 미검증 항목이 거기 있으므로 읽을 가치는 있지만, 그것을 기다려 커밋을 미루지 마라

역으로: 보고서가 왔다고 게이트를 건너뛰지 마라. 보고서는 증거가 아니다.

#### 스폰 직후 스모크 테스트 (권장)
웨이브를 크게 띄우기 전에, **haiku로 30초짜리 더미 태스크 1개**를 먼저 던져 산출이 나오는지 본다. 파일 하나 쓰고 끝내는 태스크면 충분하다. 이 30초가 위 두 세션분의 손실을 막는다.

산출물 대기는 백그라운드 `until` 루프로:
```bash
until [ -f <산출물> ]; do sleep 20; done; echo READY
```

## 2-b. 위임이 통째로 불가능할 때 — 직접 수행 폴백 ⚠️

서브에이전트가 **환경 문제로** 전부 죽는 상황이 실제로 있다(위 `teammateMode` 함정이 대표적). 이때 공장을 멈추지 마라. 실측 사례에서 10개 연속 실패 후 직접 수행으로 전환해 완료했다.

**전환 판정 — 이 중 하나면 즉시 폴백:**
- 스모크 테스트가 2분 내 산출 0
- 연속 2개 에이전트가 미기동
- 원인이 환경 설정이고, 고치려면 세션 재시작이 필요한데 지금 진행해야 함

**폴백 절차:**
1. **선언한다.** 오너에게 한 줄로 알린다 — "위임 불가, 직접 수행으로 전환". 조용히 바꾸면 나중에 "왜 병렬로 안 했나"가 된다.
2. **범위를 줄이지 마라.** 직접 수행은 느릴 뿐 산출물이 작아질 이유가 없다. 티켓을 자르려면 그건 별도의 오너 결정이다.
3. **순서를 바꾼다.** 병렬 웨이브는 파일 소유권으로 나눴지만, 직접 수행은 **의존성 순서**가 유일한 제약이다. 키스톤 → 직속 의존 → 나머지로 재정렬한다.
4. **CTO 게이트는 그대로 유지한다.** 내가 짰다고 리뷰를 건너뛰면 공장의 의미가 사라진다. 특히 §3-2(직접 실행)와 §3-3(적대적 검토)은 자기 코드에 더 엄하게 적용한다.
5. **환경 결함을 기록한다.** 원인·조치·"새 세션에서 검증할 것"을 인수인계 문서에 남긴다. 같은 함정을 다음 세션이 또 밟는 게 최악이다.

**하이브리드가 보통 최선이다:** 위임이 되는 환경이어도, 오너 결정·개명·정합성 정리처럼 **파일이 전역으로 겹치는 작업**은 직접 하고, 파일 소유권이 깔끔한 티켓만 위임한다.

## 3. CTO 리뷰 게이트 (티켓마다)

에이전트의 "완료"는 승인이 아니다. 5개 전부 통과해야 커밋·이슈 종료.

### 체크리스트
- [ ] **1. AC 전항목 증거 대조** — 티켓 AC 체크박스마다 "무엇으로 증명됐나". 증거 없는 항목 = 미완료
- [ ] **2. 직접 실행** — 빌드·린트·테스트를 내가 돌린다. 보고서의 "통과"를 믿지 않는다. 실패하면 실패로 보고
- [ ] **3. 적대적 검토** — 어떻게 깨뜨리나. **특히 프로젝트 자신의 원칙을 위반하는지** (예: "결정론" 표방인데 비결정 요소, "증거 없는 데이터 금지" 표방인데 무검증 경로)
- [ ] **4. 스코프** — 지시 외 변경 / 불필요한 추상화 / 미래를 위한 선제 설계 / 미사용 코드
- [ ] **5. 일관성** — 공개 문서(README·다국어본)·ADR 결정과 어긋나지 않는지

### 불통과 시
"다시 해봐" 금지. 다음 형식:
> **문제**: <무엇이> <왜> 틀렸는지
> **통과 조건**: 어떤 상태가 되면 승인인지 (기계 판정 가능하게)
> **하지 말 것**: 곁가지 수정 금지

같은 지시 3회 반복 금지 — 접근을 바꾸거나 오너 에스컬레이션.

### 통과 시
1. 커밋 (프로젝트 규약 도그푸딩 — 결정 맥락을 커밋 메시지에)
2. `gh issue close <n> --comment "<AC 증거 요약>"`
3. 다음 웨이브 즉시 착수

## 4. 진행 가시성

- **Remote Control**이 있으면 별도 진행 보드를 만들지 마라 — 두 번째 진실 원천이 되어 낡는다
- 마일스톤 진행률은 GitHub이 자동 계산한다 (`gh api repos/$R/milestones`)
- 오너 알림: 마일스톤 완료·에스컬레이션 시점에만 `PushNotification`. 티켓 하나하나는 알리지 않는다

## 5. 에스컬레이션 기준

즉시 오너에게 올린다:
- 존재론적 리스크 검증(벤치 등)에서 가설이 기각됨
- 같은 접근 3회 실패
- 비가역 결정(공개 전환·배포·라이선스·외부 계정)
- 범위가 오너 확정 사항과 충돌
