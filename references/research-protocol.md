# Phase 1 상세 — 증거 수집 프로토콜

## A. 학술 계보 축 설계

씨앗의 도메인에 맞춰 8~10축을 만든다. 아래는 "소프트웨어 도구/에이전트" 도메인의 실제 사용 예시 — 도메인이 다르면 축 이름만 갈아끼운다.

| 축 | 무엇을 찾나 |
|---|---|
| 1 | **이 문제의 고전** — 최초 정식화, 왜 미해결로 남았나 (실패 원인 논문이 가장 중요) |
| 2 | 인접 분야의 확립된 해법 (부분 해결) |
| 3 | 도메인 실증 연구 — 문제의 크기를 계량한 논문 |
| 4 | 데이터/현장 마이닝 연구 |
| 5 | 비용·손실의 계량 (세일즈/도입 논거가 됨) |
| 6 | 최신 시스템 계열 (최근 3년) |
| 7 | 인접 기술 스택 (메모리·검색·오케스트레이션 등) |
| 8 | 표준·규격·추적성 |
| 9+ | **보안·악용 표면** (도구가 공격면을 만드는가) |
| 10 | **실증 반증군** (→ C단계와 합류) |

축마다 요구할 것: 제목 / 저자 / 연도 / 학회·저널 / DOI 또는 arXiv ID / OA 원문 URL / 1줄 관련성. DOI 기반 중복 제거.

> ⚠️ 검색 위임 시 "존재하지 않는 DOI를 만들지 마라"를 프롬프트에 명시하고, 받은 목록은 **반드시** `scripts/verify-citations.py`로 대조한다. 실전에서 재출판본 DOI가 원판을 가리는 오매칭이 다수 발생했다.
>
> **검증 항목은 `query`가 아니라 `doi`로 넣어라.** Crossref의 서지 검색은 유명한 논문에서도 엉뚱한 것을 1순위로 돌려준다 — 실측으로 "Attention is all you need"를 검색했더니 제목이 비슷한 2026년 보안 논문이 나왔다. `expect_author`가 그 오매칭을 잡아주긴 하지만, 그건 **탐지**이지 해결이 아니다. DOI를 아는 항목은 DOI로 넣고, 모르는 항목만 `query`로 넣되 결과를 눈으로 확인한다.

## B. 경쟁·선행 제품

3가지 각도로 각각 검색한다 (한 각도로 "없다"고 결론 내리지 마라):
1. **제품 각도** — 상용 SaaS, 가격/조달 규모
2. **OSS 각도** — GitHub 토픽·유사 이름
3. **학술 시스템 각도** — 같은 문제의 프로토타입 논문

각 경쟁자마다: 접근 축 / 무게(인프라 비용) / 한계 / 우리 대비 위치.
**가장 가까운 인접자(nearest neighbor)**를 명시적으로 지목하라 — 그 존재는 위협이자 시장 타이밍 검증이고, 그 약점이 곧 우리의 차별점이 된다.

## C. 반증 증거 (필수, 위임 금지)

검색어 패턴:
```
"<핵심 개념> negative results"
"<핵심 개념> does not outperform"
"<핵심 개념> pitfalls" / "harmful" / "hurts"
"<핵심 개념> ablation study"
"why <핵심 개념> failed"
```

찾은 반증은 보고서에서 **가장 불리한 것부터** 배치한다. 그리고 다음 형식으로 답한다:

> 이 실패의 조건은 A, B, C였다. 우리 설계는 A→A', B→B', C→C'로 각 조건을 뒤집는다. **이 주장 자체가 검증 대상이므로** 벤치마크에 어블레이션(각 조건을 제거했을 때의 성능 곡선)을 1급 실험으로 편성한다.

반증에 답할 수 없으면 그것이 프로젝트의 **존재론적 리스크**다. 로드맵 최전방에 검증 티켓을 배치하고, 실패 시 피벗 판단을 오너에게 에스컬레이션하도록 ADR에 명시한다.

## D. 재현 실험 설계

목적: 레퍼런스의 주장을 직접 깨뜨려 결함을 *증명*한다.

절차:
1. 격리 환경 생성 (임시 디렉토리, `git init`, 빈 프로젝트 등 — 사용자 환경 오염 금지)
2. 레퍼런스가 주장하는 속성을 문장으로 적는다 ("X는 영구 보존된다")
3. 그 문장을 깨는 최소 시나리오를 실행한다 (표준 워크플로우 안에서 — 억지 조건 금지)
4. 명령어와 출력을 그대로 캡처
5. 판정: 깨졌으면 **결함(재현됨)**, 안 깨졌으면 주장 유효로 기록

주의:
- **억지 반례 금지.** 표준 워크플로우(기본 병합 전략, 흔한 리팩터링)에서 깨지는 것만 결함이다.
- 재현 실패한 의심은 "의심"으로 남기고 결함으로 승격하지 않는다.
- 서술은 정밀하게. "아무것도 남지 않는다"보다 "텍스트로는 남을 수 있으나 기계 조회 가능한 형태로는 소멸한다"가 리뷰를 통과한다.

## D-2. 효용 가설을 실제로 측정할 때 ⚠️

프로젝트가 "X를 개선한다"고 주장하면, 그것을 **측정하는 티켓**이 로드맵에 있어야 하고(§Phase 1-C 반증의 짝), 그 측정은 **프로젝트에 불리한 답을 낼 수 있어야** 한다. 아래는 실제로 한 번 돌려보며 얻은 것들이다.

### 1. 대조군이 처치 없이도 정답에 도달하면 그 과제는 아무것도 측정하지 않는다

가장 비싼 실패는 통계가 아니라 **과제 설계**에서 난다. 실측 사례: 대조군 7런 중 5런이 "막으려던 접근"을 **언급조차 하지 않았다.** 프롬프트가 가리킨 파일 안에서 증상을 국소적으로 고쳐 버렸고, 그건 거의 정답 해법이었다. 처치가 막을 것이 애초에 없었던 것이다.

> **과제는 그 증상이 문제의 결정을 정면으로 마주하지 않고는 해결될 수 없을 때만 측정력을 갖는다.**

설계 후 **반드시 확인**: 대조군 트랜스크립트를 읽어라. 대조군이 무엇을 했는지 표로 만들어라. 처치 없이 정답에 닿았다면 그 과제는 효과를 0 쪽으로 희석할 뿐이다.

### 2. 사후에 부분집합을 골라 p값을 내지 마라

위 발견을 하고 나면 "판별력 있는 과제만 골라 다시 계산"하고 싶어진다. **그건 데이터를 보고 분석 대상을 고르는 것이다.**

- **주 결과** = 사전에 정한 전수. 숫자로 제시되는 유일한 결과
- **사후 관찰** = 한계로 서술. "N개가 판별력이 없었으므로 주 결과는 **효과의 하한**이다"까지가 최대
- 부분집합 p값은 **계산해서 싣지 마라.** 싣고 싶으면 "하지 않았다, 이유는 이것" 이라고 쓰라
- 발견의 정당한 사용처는 **다음 반복의 설계 규칙**이다

### 3. 통계 구현은 독립적으로 교차 검증하라

프로젝트의 **가장 중요한 숫자**를 만드는 코드는 위임한 채로 믿지 마라. 실측 절차:
1. 같은 통계를 **직접 다시 구현**한다(짧다 — Fisher exact는 로그감마 + 초기하 합)
2. 그것을 먼저 **공표된 값**과 맞춘다(R `fisher.test` 등, 4~5개 표)
3. 그 다음 에이전트 구현과 **여러 표에서 대조**한다

실측 결과 p값은 7/7 일치했고 — **오즈비에서 결함이 나왔다.** 0 셀이 있는 표에서 `OR=0`을 반환했는데, 그건 "처치군의 오즈가 0"으로 읽힌다. 실제로는 **관측되지 않았을 뿐**이고 n이 작으면 0이 아니라 작다는 것까지만 말할 수 있다. 0 셀은 `null` + 사유, 또는 조건부 MLE, 또는 보정했다고 **명시**한 보정값이어야 한다.

### 3-b. 파일럿과 본실험을 나눠라 — 그리고 그 차이를 문서에 써라

첫 측정은 **파일럿으로 취급하라.** 파일럿에서 나오는 것은 수치가 아니라 **설계 결함**이다: 판별력 없는 과제, 탐지기 오탐, 비현실적인 예산, 하니스 버그.

**정당한 것 / 금지된 것**의 선이 여기서 갈린다:

| 파일럿을 보고 고쳐도 되는 것 | 절대 금지 |
|---|---|
| 명시된 **속성**에 맞게 과제를 다시 쓰기 | 어떤 과제가 **효과를 보였는지**를 보고 고르기 |
| 탐지기 오탐·오작동 수정 | 지표를 넓혀 원하는 방향의 수치를 만들기 |
| 실측 소요에 근거한 예산 조정 | 결과를 보고 분석 대상을 고르기 |

**본실험 전에 사전 등록하라.** 최종 과제 목록과 각각의 선정 근거, 최종 판정 규칙과 파일럿 대비 변경 내역, 조건·seed·모델·예산, **주 가설과 그것을 검정할 표 하나**, 그리고 "부분집합 분석은 하지 않는다"를 파일에 적고 **그 다음에** 돌린다.

⚠️ **파일럿 데이터로 p값을 계산해 보고하지 마라.** 집계는 해도 되지만 "파일럿"이라고 붙이고, 인용 대상이 아님을 파일 안에 남겨라.

### 3-c. 수치를 만든 코드가 사라지면 그 수치는 재현 불가다

**측정 전에 코드를 동결하고, 그 시점의 커밋 SHA를 결과 파일에 박아라.** 그게 없으면 "seed 고정 재실행으로 재현"이라는 AC는 영구히 충족할 수 없다.

실측 사례: 60런 매트릭스가 도는 동안 다른 에이전트가 러너와 주입기 파일을 편집했다. 매트릭스는 **오염되지 않았다**(§아래 참조) — 그런데도 그 결과 파일은 폐기해야 했다. **그 수치를 만든 코드가 저장소에 더 이상 존재하지 않아서** 누구도 재실행해 복원할 수 없기 때문이다.

- 장기 측정 전: 관련 파일을 커밋하고 **SHA를 manifest에 기록**한다
- 측정 중: 그 파일들과 실행 중 프로세스가 읽는 전체 모듈 그래프를 동결
- 이미 벌어졌으면 되돌리지 마라. **파일럿으로 강등**하고 동결 후 재실행한다
- 재실행할 거라면 **설계도 함께 고쳐라.** 재현성만 복구하고 설계를 두면 "재현 가능한 무의미한 결과"가 나온다

### 3-d. ⚠️ 파일 mtime으로 실행 중인 프로세스의 코드를 추론하지 마라

위 사례에서 나는 **"파일이 43번째 런 시점에 바뀌었으니 44번 이후는 다른 코드로 돈다"**고 판단하고 그 근거로 전량 재실행을 지시했다. **틀렸다.** 담당 에이전트가 반박했고 검증해 보니 그쪽이 맞았다:

```
grep -rn "await import|require(" <실행 파일들>   → 0건 (전부 정적 import)
ps -eo pid,lstart,etime,command | grep runner    → 단일 PID, 매트릭스 시작 시각부터 연속
```

Node를 비롯한 대부분의 런타임은 **정적 import를 기동 시 1회 로드·캐시하고 핫리로드하지 않는다.** 디스크 편집은 이미 돌고 있는 프로세스에 도달하지 못한다. 60런 전부가 기동 시점의 단일 코드 버전으로 실행됐다.

**절차**: 실행 중인 프로세스가 무슨 코드를 쓰는지 알고 싶으면 **프로세스를 봐라**, 파일을 보지 말고. 강한 신호부터:

1. **모듈 그래프가 그 파일에 닿기는 하는가** — 가장 강한 답이다. `grep`으로 import 경로를 훑고, 빌드 경계(`rootDir`, workspace 분리, 번들 entry)가 **구조적으로 불가능**하게 만드는지 본다. 이건 "확인"이 아니라 **증명**이다. 실측 사례에서 문제의 파일은 `tsconfig.json`의 `rootDir` 때문에 애초에 import될 수 없었고, 그것 하나로 논쟁이 끝났다
2. **프로세스 수명** — `ps -eo pid,lstart,etime,command`로 PID와 **기동 시각**. 측정 시작 시각부터 연속인가, 런마다 새로 뜨는가
3. **동적 로딩 여부** — `await import` / `require()` / 설정 리로드 / 파일 워처. 하나도 없으면 기동 시 캐시된 코드가 전부다
4. **산출물의 실행 식별자** — 결과에 `run_id` 같은 것이 있으면 개수를 세라. 재시작이 있었다면 두 개다
5. 런마다 프로세스를 새로 띄우는 하네스라면 그때는 **실제로** 도중 변경이 반영된다 — 그 경우에만 분할이 일어난다

⚠️ 그리고 **장기 실행 프로세스는 죽을 수 있다.** 위 사례에서 러너는 57/60에서 죽었고, 래퍼의 exit 줄조차 남기지 못했다. 그 상태에서 같은 출력 파일로 **재개하면 그때는 진짜로 두 코드 버전이 섞인다** — 지금까지 없던 오염을 재개가 만든다. 죽은 측정은 **그 자리에서 봉인**하고, 행 수·불균형·종료 사유를 결과에 기록하라.

이 구분을 안 하면 멀쩡한 측정을 버리거나(내가 할 뻔했다), 오염된 측정을 발표하게 된다. 둘 다 비싸다.

> 부수 교훈: **에이전트가 내 판단을 반박하면 근거부터 검증하라.** 이 건은 담당자가 `ps`와 `grep` 출력을 들고 왔고, 확인해 보니 내 추론이 틀렸다. 반박을 검증 없이 기각했다면 60런을 헛되이 다시 돌렸을 것이다.

### 4. 측정 조건을 기록에 남겨라

수치는 조건부다. 모델·버전·seed·예산·날짜가 결과 파일이나 manifest에 없으면 그 수치는 재현 불가능하고, 6개월 뒤에는 인용도 불가능하다. 특히 **어떤 필드가 러너가 직접 쓴 것이고 어떤 필드가 사후에 스탬프된 것인지**까지 적어라.

### 5. 정지 라벨이 통제를 과장하지 않게 하라

"예산 초과로 멈췄다"와 "예산을 넘긴 것을 나중에 관측했다"는 다르다. 실행기가 실제로 멈출 수 없는 예산이라면 라벨이 그렇게 말해야 한다. 자기 통제력을 과장하는 벤치마크는 숫자도 믿을 수 없다.

## E. 인접 개념 차용 판정

오너가 참고자료(글·논문·영상)를 줄 때마다 판정표를 만든다:

| 항목 | 개념 | 판정 | 귀속 |
|---|---|---|---|
| step N | ... | 차용 / 차용(재해석) / 기각 | 설계상 어디로 갔나 |

규칙:
- **기각도 기록한다.** 이유 없는 기각은 반드시 재논의된다.
- 차용은 "어디에 귀속됐는지"까지 써야 유효하다. 귀속 없는 차용은 장식이다.
- 여러 자료가 같은 규율에 수렴하면 그것은 **독립 교차 검증**이므로 그 사실 자체를 기록한다.

## 차단 사이트 대응

X(트위터) 아티클, 로그인 벽 사이트 등은 `insane-search` 스킬 경유. 실전 경로:
1. syndication API로 메타데이터 확보 (제목·저자·본문 링크 식별)
2. 본문이 로그인 벽이면 **미러 검색** (요약 사이트, gist, 필드노트)
3. 자매편·후속 글로 우회
4. 전부 실패하면 실패로 보고. 추측으로 채우지 마라.
