# 자가개선 루프 — 프로젝트가 스킬을 검사하는 구조

이 문서는 repo-factory가 실사용에서 나온 결함을 스킬 자신의 게이트·불변식으로
승격시키는 최소 구조를 정의한다.

## 왜 이 문서가 필요한가

여러 프로젝트를 지어보면 루프는 **작동하지만 수동**이다. 실제 프로젝트를 돌린
것이 스킬의 결함을 여러 건 냈고, 그중 어느 것도 테스트가 미리 잡지 못했다.
발견에서 수정까지의 연결은 운영자가 직접 했다 — 운영자가 빠지면 루프도 멈춘다.

동시에 반복된 실패가 있다. **검증 대상과 실제 작동물이 어긋난 것**이 나흘간
다섯 번이었다:

| 무엇을 봤나 | 실제로 작동한 것 |
|---|---|
| 로컬 테스트 통과 | CI는 5커밋 연속 빨간불 |
| 커밋 해시 동결 | 러너가 읽는 배포 산출물의 바이트는 계속 바뀜 |
| 진입점 파일 해시 | 바뀐 것은 그 파일이 임포트하는 모듈 |
| YAML 파서 통과 | GitHub은 워크플로로 거부 |
| Phase 4 체크리스트 | 정지선이 아니어서 산출물을 건너뜀 |

루프의 목적은 새 기능을 만드는 것이 아니라 **이 어긋남을 기계가 먼저 발견하게**
하는 것이다.

---

## 스킬과 프로젝트의 관계

```
        ┌──────────────── 공장 스킬 ────────────────┐
        │   Phase 게이트 · 브랜치 모델 · 티어(S/M/L)  │
        └───────┬─────────────────────────┬─────────┘
                │ 짓는다                  │
                ▼                         │
          신규 프로젝트                   │
                │                         │
                └──── 실사용에서 결함 발견 ─┘
                          │
                          ▼
                게이트/불변식으로 승격할지 판단
```

- **스킬 → 프로젝트**: 게이트가 통과하지 않으면 다음 Phase가 시작되지 않는다.
  체크리스트가 아니라 `phase-gate.py`의 exit code다.
- **프로젝트 → 스킬**: 실사용에서 나온 결함이 스킬의 게이트·불변식으로 승격된다.

## 루프 1회 — 무엇을 어떤 순서로 돌리는가

### 1. 상태 판정 (기계)

```bash
python3 scripts/phase-gate.py 4 --repo <owner/name> --path <checkout> --tier <S|M|L>
```

**exit code만 믿는다.** 파이프 뒤에서 `$?`를 읽지 마라 — 그 실수를 하루에 두 번
했다.

### 2. CI 확인 (기계, 로컬 아님)

```bash
gh run list --repo <owner/name> --limit 1 --json headSha,conclusion
```

로컬 스위트 통과는 CI 통과가 아니다. 다섯 번 그렇게 말했고 다섯 번 틀렸다.
**푸시한 HEAD에서 `success`를 눈으로 본 뒤에만 "초록"이라고 쓴다.**

### 3. 결함 분류 — 그 프로젝트만의 문제인가, 스킬의 문제인가

| 증상 | 귀속 |
|---|---|
| 프로젝트가 규약을 못 지킨다 (그 프로젝트 안에서만 관측됨) | 그 프로젝트를 고친다 |
| **같은 형태가 두 번째 프로젝트에서도 나온다** | **스킬 결함 — 게이트나 불변식을 만든다** |

두 번째 줄이 루프의 심장이다. **한 번은 버그, 두 번은 스킬 결함이다.**

### 4. 수정 → 사건으로 검증

수정이 자기 테스트를 통과하는 것은 증거가 아니다. **원래 사건을 재현해서 그것이
막히는지 본다.**

실증 예: 어떤 산출물 해시 검사가 처음엔 진입점 파일만 해싱했다. 자기 테스트는
전부 통과했다. 실제로 문제를 일으킨 변경(진입점이 임포트하는 다른 모듈)에 대고
재보니 감지하지 못했다 — 자기 테스트가 재현하는 시나리오와 실제 사건이 달랐다.

### 5. 되먹임 승격

수정이 끝나면 묻는다: **이 결함이 다음 프로젝트에서도 가능한가?**

- 아니오 → 그 프로젝트 안에서 끝
- 예 → 스킬에 게이트 또는 불변식으로 승격. 반드시 **명령으로 판정 가능한 형태로**

## 루프가 멈추지 않게 하는 세 가지

### 정지선은 명령이어야 한다 (불변식 11)

체크리스트는 요약으로 읽힌다. `phase-gate.py`가 exit 2를 내면 다음 단계가
시작되지 않는다. 실측 사례: 한 프로젝트 실행에서 체크리스트를 완료 요약으로
읽어 마일스톤·이슈·CONTRIBUTING을 통째로 건너뛴 채 다음 Phase를 시작했다 —
목록이 없어서가 아니라 **목록이 정지선이 아니어서**였다.

### 게이트는 거짓 실패를 내면 안 된다

`Backlog (post-v0.1)`를 `Backlog` 정확 일치로 검사해 거짓 FAIL을 낸 적이 있다.
**운영자가 틀렸다고 아는 실패를 내는 게이트는 대충 넘겨보게 되고, 그러면 진짜를
놓친다** — 게이트가 막으려던 바로 그 실패다. 게이트를 고칠 때는 진짜 실패가
여전히 실패하는지 함께 확인한다.

### 위임 보고는 주장이지 결과가 아니다

- 테스트 수만 보고받지 말고 항목별 합격 수도 받는다. 다른 작업이 같은
  워크트리에 쓰는 중이면 부분 수집이 일어난다(실측: 1108건 기준에 943건 보고된
  사례 — 동시 실행 중 일부만 수집됐다).
- `git add -A` 금지. 무관한 문서가 다른 커밋에 실려간 적이 있다.
- 위임이 "검증 통과"라고 하면 **무엇으로 검증했는지** 확인한다. YAML 파서 통과를
  GitHub 워크플로 유효성으로 보고한 사례가 있다.

## 완결 조건 — 판정 가능한 상태로 적는다

기한이 아니라 판정 가능한 상태로 적는다.

**개별 프로젝트** — `phase-gate.py`가 그 프로젝트의 티어에서 exit 0이고, CI가
초록이다.

**스킬 자신** — 프로젝트 두 개 이상을 짓는 동안 발견된 반복 결함 형태가 전부
게이트 또는 불변식이 되어 있고, 각 게이트가 **진짜 결손에서 실패하고 정상
상태에서 통과하는 것**이 실증되어 있다.

프로젝트를 더 짓지 않으면 스킬은 개선되지 않는다.

## 부록 — 실제로 당한 함정

내용 자체는 특정 레포가 아니라 **이 공장으로 짓는 모든 프로젝트**에 적용된다.
신원(레포 이름·커밋 해시·이슈 번호)은 지웠다 — 패턴만 남긴다.

| 금지 | 무슨 일이 있었나 |
|---|---|
| `git add -A` | 무관한 문서 두 개가 다른 커밋에 실려갔다. 두 번. 경로를 지정해 커밋한다 |
| `git reset --hard` | 커밋 안 된 파일 세 개가 사라졌다. 위임이 도는 중에는 특히 금물 |
| 파이프 뒤의 `$?` | `cmd \| sed` 뒤의 `$?`는 sed의 것이다. 게이트 exit code를 두 번 오판했다 |
| 벤치를 워킹 트리에서 실행 | 훅이 배포 산출물을 살아있는 워킹 카피에서 읽는다. 12시간 동안 8번 재빌드해 측정이 무효가 됐다 |
| 위임 보고를 결과로 취급 | 1108 기준에 943 통과를 보고받았다(동시 실행 중 부분 수집). 항목별 합격 수도 함께 받고 직접 재현한다 |
| 레포당 위임 2건 동시 | 위 사례의 원인. 다른 레포끼리는 병렬 가능, 같은 워크트리는 순차 |
| 위임을 잘못된 루트로 띄우기 | 작업 디렉터리가 A인데 B도 고치라고 시켰다. 쓸 수 없어서 조용히 안 됐고, 게이트가 정상 레포를 실패시켰다 |

### 검증할 때 흔히 어긋나는 짝

왼쪽을 보고 오른쪽을 봤다고 착각한 사례들이다. 나흘간 다섯 번 반복됐다.

| 본 것 | 실제로 작동한 것 |
|---|---|
| 로컬 스위트 통과 | CI (8커밋 연속 빨간불) |
| 커밋 해시 동결 | 러너가 읽는 바이트 |
| 진입점 파일 해시 | 그 파일이 임포트하는 모듈 |
| YAML 파서 통과 | GitHub의 워크플로 수용 |
| 체크리스트 존재 | 정지선 |

**규칙: 검증했다고 쓰기 전에, 검증한 대상과 실제로 작동하는 대상이 같은지 한 번 더 묻는다.**

### 무언의 스킵 — 이름을 얻은 뒤에도 재발했다

같은 결함이 표면만 바꿔 반복됐다: **검사가 답은 했는데, 무엇을 못 봤는지는
말하지 않았다.** exit 0을 냈고 때로는 stdout도 냈으므로 "검사가 멈췄다"와는
다르다 — 검사는 끝까지 돌았고, 그저 자기 대답의 범위를 밝히지 않았다.

관측된 형태(전부 실제 사건이었다 — 어느 프로젝트인지, 어떤 도구인지는 지우고
패턴만 남긴다):

| # | 무슨 일이 있었나 |
|---|---|
| 1 | 참조 id가 실제로 존재하는지 확인하는 클래스 자체가 없어서, 존재하지 않는 레코드를 가리켜도 exit 0으로 조용히 통과했다 |
| 2 | 병합 방식(squash 등)이 앞선 기록 블록을 본문에 그대로 붙였는데, 파서는 메시지의 마지막 문단만 읽어 앞선 레코드가 조용히 산문이 됐다 — 그런데도 "메시지가 멀쩡하다"고 답했다 |
| 3 | 자동 수정 도구가 방금 쓴 설정 줄을 "ok"로 보고했지만, 그 설정을 실제로 검증하는 명령을 한 번도 실행하지 않아 실패가 계속 숨어 있었다 — 자신의 안내 문서가 실행하라고 한 바로 그 명령이었다 |
| 4 | 얕은 클론 위에서 답하면서 이력이 잘렸다는 언급이 전혀 없었다. CI 체크아웃 기본값이 얕은 클론이라 구조적으로 눈멀었는데 exit 0으로 끝났다 |
| 5 | 깨진 입력과 정상 입력이 exit 0·출력 0으로 바이트 단위 동일했다 — 하나는 고장, 하나는 정상인데 구별할 수 없었다 |
| 6 | 형식상 사소한 차이(빈 줄 하나)로 파서가 기록 블록 전체를 산문으로 읽었고, 아무 출력 없이 exit 0을 냈다 |
| 7 | 같은 입력을 서로 다른 두 명령에 넣었더니 답이 서로 달랐다 — 어느 쪽도 자기 답이 다른 명령의 답과 어긋난다는 것을 말하지 않았다 |

이 형태에 이름이 생긴 뒤에도(관련 검사가 스스로 "엄격도가 아니라 필요한 정보"로
분류를 나눈 뒤에도) 같은 결함이 재발했다. 원인은 분류가 틀려서가 아니라, 그
분류가 **명령 하나의 설계 안에만** 살았기 때문이다 — 관련된 다른 명령들은 각자
따로 같은 실수를 다시 저지를 수 있었고, 실제로 저질렀다.

| 클래스 | 질문 | 필요한 것 | 돌 수 있는 곳 |
|---|---|---|---|
| Shape | 형식이 맞는가 | 입력 자체 | 어디서든 |
| Reference | 이 id가 정확히 하나로 풀리는가 | 외부 상태(레포 등) | 그 상태에 연결됐을 때만 |
| Conservation | 이 변환에서 살아남았는가 | 전·후 상태 | 변환 전후 둘 다 볼 수 있을 때만 |

규칙 하나: **클래스를 실행할 정보가 없으면 그 클래스는 "not-checked"로 보고하고,
통과와 절대 같은 모양으로 찍지 않는다.**

**한 도구의 스펙에 적히는 것과, 그 도구를 짓는 공장의 게이트가 되는 것은
다르다.** 후자만 다음 프로젝트에 자동으로 전파된다 — 그래서 SKILL.md 불변식
12가 있다: 이 분류를 특정 도구 하나가 아니라, **이 스킬이 내놓는 모든
검사**(게이트·CI 스텝·검증 스크립트)가 각자 기계로 재확인해야 한다는 원칙으로
일반화했다.

### 인수인계 문서를 만들지 마라

새 세션을 위한 별도 문서는 필요 없다. 필요한 것은 전부 **검사받는 자리**에
있어야 한다: 남은 작업과 순서는 게이트가 판정하고, 결정 이력은 ADR과 커밋에
남고, 진행 항목은 GitHub 이슈가 추적한다. 별도 인수인계 문서는 이것들의
**검사받지 않는 사본**이고, 사본은 원본보다 먼저 썩는다.

## 위임 브리프는 제로 컨텍스트여야 한다 — 측정 타당성 조건

결정 기록(ADR의 `Rejected:` 절 등)을 남기는 이유는 **기각된 접근이 되살아나는
것을 막기 위해서**다. 그런데 티켓 브리프를 쓰는 사람은 이미 그 결정을 알고
있고, 무심코 브리프에 적는다.

> "보안을 점수에 합치지 마라 — ADR-0012가 기각했다"

이 한 줄이 들어가는 순간 에이전트는 **브리프를 따른 것**이고, 결정 기록이 한
일은 없다. 그 실행에서 관측한 준수는 기록 자체가 잘 작동했는지에 대해 아무것도
말해주지 않는다.

**실제로 일어난 일**: 한 프로젝트의 설정용 브리프 하나가 기각 대안을 스무 곳에서
그대로 알려줬다. 결정 기록이 지키려던 바로 그 선택지들을 이름까지.

### 규칙

기록이 알려주기로 되어 있는 것을 브리프가 먼저 알려주면 안 된다.

**브리프에 쓸 수 있는 것**: 무엇을 만드는가 · 판정될 AC · 소유 파일 경계 ·
테스트 실행법

**브리프에 쓸 수 없는 것**: 어떤 대안이 왜 기각됐는가 · 기각 기록의 내용 · 어떤
접근이 검토 후 버려졌다는 사실 · 읽으라고 지시하지 않은 ADR의 결론

에이전트가 제약을 알아야 한다면 **결정 기록을 직접 조회하는 경로**로 도달해야
한다(착수 전 확인 단계, 별도 질의 등) — 브리프가 대신 요약해주면 안 된다.

### 예외

검증 과제("이 명령을 돌리고 출력을 보고하라")는 설계 선택을 담지 않으므로 해당
없다. 측정 과제는 자기 방법을 서술해도 된다.

### 대가

브리프가 짧아지고 쓰기 불편해진다. 운영자는 에이전트를 알려진 정답으로 몰아갈
능력을 잃는데, **그 능력의 부재가 바로 측정 대상이다.** 새는 브리프였다면 한
번에 맞혔을 작업을 다시 하게 되고, 그 재작업 비용이 곧 측정값이다.

## Factory defect 승격 규칙 (2026-08-08 — 운영 커널 도입과 함께)

생성된 레포에서 문제가 났을 때 그것이 프로젝트 버그인지 공장 결함인지의 판정:

- 한 번은 project bug 다. **두 프로젝트에서 반복되면 factory defect** 다.
- 단, security 사고 · wrong merge · false verified 는 **한 번으로 factory P0** 다.
- defect 는 재현 fixture(`tests/`) 없이 factory rule 로 승격하지 않는다 — 규칙만
  늘리고 검출은 못 하는 문서는 부채다.
- **status-only PR 이 필요해졌다면** 그 자체가 factory defect 다 (현재 상태는
  커밋하는 것이 아니라 매번 재계산하는 것이다).
- **mode switch 가 필요해졌다면** 설계 실패 신호다 — 모드는
  `single_owner_policy_delegated_autonomy` 하나뿐이어야 한다.
- current tree 와 historical merge 를 구분하라. issue/label/roadmap 은 projection
  이다. owner 와 authenticated actor 를 구분하라.
- policy copy drift 는 기계 검사다 (`governance.py validate` 의 POLICY_DUPLICATE).
- gate 가 거짓 실패를 내면 정상/결손 **양방향 fixture** 를 만들어라.
- mutation harness 자체도 언젠가 mutation test 대상이 된다 — 하드코딩된 case
  목록, equivalent mutant 를 killed 로 세는 버그, runner crash 를 killed 로 세는
  버그가 실제 함정이다.
