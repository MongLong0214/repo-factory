# 자가개선 루프 — 도그푸딩을 게이트로 만들기

SKILL.md 불변식 7의 상세. **프로젝트가 주장하는 것을 프로젝트 자신이 지키게 만들되, 사람의 기억이 아니라 빌드가 강제하게 한다.**

이 문서는 "도그푸딩 하세요"가 아니다. 도그푸딩을 **실패할 수 있는 검사**로 바꾸고, 그 실패가 프로젝트를 개선하게 만드는 구조에 관한 것이다.

---

## 왜 관행으로는 안 되는가

"우리는 우리 규약을 지킵니다"는 검증 불가능한 주장이다. 실측 사례에서, 스펙 프로젝트의 **README 대표 예제가 자기 스펙을 위반한 채** 4개 언어로 배포돼 있었고 산문 리뷰 두 번과 개명 한 번을 통과했다. 같은 프로젝트의 커밋 기록 3건은 자기 검증기에 거부됐다.

둘 다 사람이 성실하지 않아서가 아니다. **기계가 안 보고 있었기 때문이다.**

---

## 루프의 6가지 규율

### 1. 게이트로 만들어라 — 관행이 아니라 실패할 수 있는 검사

프로젝트가 무언가를 정의한다면(포맷·프로토콜·규약·API), 그 정의를 **자기 산출물에 적용하는 테스트**를 쓴다.

| 프로젝트가 정의하는 것 | 도그푸딩 게이트 |
|---|---|
| 커밋 메시지 규약 | 자기 git 히스토리를 검증기에 통과시킨다 |
| 설정 파일 스키마 | 자기 저장소의 설정 파일을 자기 스키마로 검증한다 |
| 코드 스타일 룰 | 자기 소스에 자기 린터를 돌린다 |
| API 응답 스키마 | 자기 예제 응답을 자기 스키마로 검증한다 |
| 문서의 예제 코드 | 예제를 픽스처로 승격해 실행·대조한다 |
| **지원 런타임·플랫폼 하한** | **CI가 그 하한에서 실제로 돈다 + 의존성이 하한을 지키는지 검사한다** |

마지막 줄이 가장 자주 빠진다. `engines`·`python_requires`·최소 OS 버전은 **약속**인데, 그것을 확인하는 것이 없으면 거짓말이 된다. 실측 사례: ADR이 Node 20을 하한으로 정했는데 의존성 두 개가 Node 22를 요구하고 있었다. npm은 `EBADENGINE`을 **경고로만** 내고 설치를 진행하므로 아무것도 멈추지 않았고, 개발자는 Node 24를 쓰고 있어 로컬에서 재현되지 않았다. **의존성을 추가하는 사람은 대개 자기가 깨뜨린 하한보다 새 런타임 위에 있다.** 드러난 경로는 CI에서 테스트 워커가 이유 없이 죽는 것이었고, 그 모듈은 이미 리뷰를 통과하고 이슈가 닫힌 뒤였다.

→ 하한 검사 스크립트를 만들고 CI 단계로 넣어라. 그리고 **CI 매트릭스는 하한과 최신을 둘 다 돈다** — 하한만 돌면 최신에서 깨지는 것을 놓치고, 최신만 돌면 하한이 아무도 확인하지 않는 주장이 된다.

그리고 **CI에 넣는다.** CI에 없으면 "강제"가 아니라 "누가 돌리면"이다.

### 2. 범위는 유도하라 — 설정하지 마라 ⚠️

프로젝트가 규약을 도입한 시점 이전의 산출물은 규약을 어긴다. 당연하다. 그래서 검사에 범위가 필요한데, **그 범위를 사람이 관리하면 반드시 낡는다. 그리고 낡은 범위는 통과처럼 보인다.**

산출물 자체에서 유도하라:
```
❌ const ADOPTION_SHA = 'abc1234';        // 손으로 관리 → 낡는다
✅ 규약 버전을 선언한 가장 오래된 산출물부터   // 히스토리에서 유도 → 자동 유지
```
실측 예: "`Convention-Version:`을 선언한 가장 오래된 커밋부터 HEAD까지". 히스토리가 늘어도 갱신할 것이 없다.

### 3. 침묵이 성공처럼 보이면 안 된다

검사가 **돌지 못한 경우**가 통과와 구별되지 않으면 그 게이트는 언젠가 조용히 죽는다.

- 얕은 클론(`fetch-depth: 1`)이면 히스토리 검사는 0건을 검사하고 초록이 된다 → **명시적으로 실패**시키고 `fetch-depth: 0`을 메시지에 적어라
- 검사 대상이 0건이면 → "최소 N건은 있어야 한다"를 별도 단언으로 둬라
- 외부 API가 죽어서 검증을 못 했으면 → `UNCHECKED`로 분류하고 **실패로 센다.** 네트워크가 죽은 것과 인용이 옳은 것은 다르다

### 3-b. 탐지기의 시험 데이터는 **남의 탐지기에는 안 걸려야** 한다 ⚠️

비밀 탐지·악성 패턴 탐지처럼 "나쁜 것"을 찾는 기능을 만들면, 그 양성 픽스처가 **호스팅 제공자의 스캐너에도 걸린다.**

실측 사례: secret guard의 Slack 양성 픽스처가 GitHub 푸시 보호에 걸려 **저장소 푸시 자체가 거부**됐다. 그런데 "명백히 가짜로 만들기"는 답이 아니다 — 잘 만든 탐지기에는 플레이스홀더 필터가 있어서(`example`, `xxxx`, 반복 문자열) 그런 값은 **자기 탐지기도 안 잡는다.**

픽스처는 두 탐지기 사이의 좁은 구간에 있어야 한다:
- **엔트로피는 진짜** — 플레이스홀더 필터를 통과할 만큼
- **구조는 가짜** — 제공자의 구조 검증을 통과하지 못할 만큼 (예: Slack의 숫자 팀/유저 ID 자리에 영숫자, AWS 키의 체크섬 불일치, 토큰 길이 어긋남)

절차:
1. 픽스처를 넣고 **커밋 전에** 자기 탐지기가 잡는지 확인
2. 푸시해서 제공자 스캐너가 통과시키는지 확인 — 막히면 값을 바꾼다. **allowlist로 우회하지 마라**(공개 저장소에 살아 보이는 자격증명이 남는다)
3. 커밋 메시지에 다음 사람을 위한 경고를 남긴다: "양성 픽스처를 추가할 땐 엔트로피는 주되 제공자 구조를 깨라"

같은 함정이 XSS 페이로드, 악성 정규식, 취약 의존성 픽스처에도 있다.

### 4. 게이트를 뮤테이션 테스트하라 ⚠️

**통과만 보고 넘어가면 아무것도 안 하는 검사를 배포한다.** 위반 유형마다 일부러 깨뜨려서 실제로 잡히는지 확인하라.

```bash
# 안전한 절차: 추적 중인 변경을 먼저 커밋한 뒤
before=$(git rev-parse HEAD)
git commit --allow-empty -F <위반이 든 메시지>
<검사 실행>            # 실패해야 한다
git reset --hard "$before"   # untracked 파일은 건드리지 않는다
```
⚠️ **`git stash`를 쓰지 마라.** 병렬 에이전트가 작업 중이면 그들의 미추적 산출물까지 통째로 치운다. 실측으로 한 번 밟았다(복구는 됐다).

실측 예: 도그푸딩 게이트에 5종(enum 위반 / 신원 누락 / 참조 끊김 / 근거 경로 부재 / 신원 중복)을 주입해 5종 모두 검출을 확인했다.

### 5. 실패의 해석은 정확히 두 가지다 — 그리고 둘 다 기록된다

| 산출물이 틀렸다 | 규칙이 틀렸다 |
|---|---|
| 관행을 고친다 | 스펙을 바꾸고, **새 규칙을 고정하는 픽스처를 추가하고**, 왜 옛 규칙이 틀렸는지 커밋에 적는다 |

**단언을 약화시켜 초록을 만드는 것은 둘 중 어느 것도 아니다.** 이 문장을 프로젝트의 CONTRIBUTING에 그대로 넣어라 — 나중에 그 유혹을 느끼는 사람이 읽을 곳이 거기다.

### 6. 루프가 스펙을 바꾼 적이 없으면, 그 루프는 현실과 만난 적이 없다

건강한 도그푸딩은 **가끔 스펙을 진다.** 실측 예: `Evidence:` 필드가 `path#anchor`를 강제했는데, 스펙에 맞춰 쓴 첫 기록들이 즉시 걸렸다 — 파일 전체를 근거로 가리키는 건 정상적인 인용이고 검증 가능성도 동일한데, 앵커 강제는 **가짜 앵커를 만들게** 할 뿐이었다. 규칙을 완화하고 양쪽 경계(허용/거부)를 픽스처로 고정했다.

게이트가 한 번도 빨간불이 된 적 없다면 의심하라. 검사가 아무것도 안 보고 있을 가능성이 높다.

## 계층: 예방 · 검출 · 재생성

셋을 다 갖춰야 루프가 닫힌다.

| 계층 | 하는 일 | 예 |
|---|---|---|
| **예방** | 위반이 애초에 들어오지 못하게 | commit-msg 훅, pre-commit, 편집기 스키마 |
| **검출** | 들어온 위반을 빌드에서 잡음 | 도그푸딩 테스트, 적합성 스위트, CI |
| **재생성** | 문서의 주장을 산출물에서 다시 만듦 | README 수치는 벤치 로그에서만, 예제는 픽스처에서 |

**검출만 있으면** 위반이 계속 들어오고 사람이 계속 고친다.
**예방만 있으면** 훅을 우회한 것과 과거 산출물이 영원히 안 잡힌다.
**재생성이 없으면** 문서가 조용히 코드와 갈라진다.

## 체크리스트

- [ ] 프로젝트가 정의하는 규약마다, 그것을 자기 산출물에 적용하는 검사가 있다
- [ ] 그 검사가 **CI에서** 돈다
- [ ] 검사 범위가 산출물에서 **유도**된다 (하드코딩된 커밋·날짜·버전 없음)
- [ ] 검사가 **돌지 못한 경우**가 실패로 보고된다 (얕은 클론, 빈 대상, 네트워크 실패)
- [ ] 위반 유형마다 **뮤테이션으로 검출을 증명**했고 그 출력을 남겼다
- [ ] 실패 시의 두 가지 해석과 "단언 약화 금지"가 CONTRIBUTING에 적혀 있다
- [ ] 문서의 기계 검증 가능한 주장(예제·수치·표)이 전부 검사에 묶여 있다
